# Ontology head: BFO 2020 / CCO v2.2

The ontology head types text with a class from the federal baseline ontology
standard: **Basic Formal Ontology** (BFO 2020, ISO/IEC 21838-2) as the
top-level ontology and the **Common Core Ontologies** (CCO v2.2) as the
mid-level one, adopted by the DoD, ODNI and CDAO chief data officers in
February 2024 (https://www.buffalo.edu/ubnow/stories/2024/03/smith-ontology-standard.html).
That class is the address key's type segment:

```
<tenant>|<w>|<class CURIE>|<entity>|<x>|<y>|<z>|<rotation>
_default_|_default_|cco:ont00001262|9050bdbe94bc|lca:..|lca:..|lca:..|xyz
```

## What the type segment means

The class of what the **record** (or sentence) is about. Every address of
Einstein's record -- including the one anchored on "Nobel Prize" -- is typed
cco:Person. A query finds records through it: the partitions holding a query
entity are exactly the classes that entity is stored under, which the graph
index lists (`idx|ent|<entity>|...` keys embed the full address key). The query
never has to infer an answer type from its wording.

## How the head classifies

1. Each sentence of the shared ParsedDocument (rule backend; the head never
   parses) becomes cues: the predicate noun of a copular clause and its
   modifiers, the subject's common-noun head, subject pronouns, appositive
   heads, other nouns and verbs, NER labels (weak). Cues are hashed into 4,096
   buckets and L2-normalised, so length does not matter. Sentences shorter
   than 3 tokens (the bare "Title." fragment) carry no cues -- except a
   list-style title the DCP adapter prepended (`List_of_...`, `Timeline_of_...`,
   `..._discography`, `National_Register_of_Historic_Places_listings_in_...`;
   `features.TITLE_KINDS`), which gives one cue, `title:<kind>`. A list page's
   abstract is often the bare list of names, so its title is the only text
   saying what the record is.
2. The codebook IDF-weights the vector and scores each class by its best
   centroid's cosine; a temperature softmax gives probabilities.
3. Resolution: the top class if its probability clears the acceptance
   threshold; else the deepest ancestor whose summed probability clears it
   (City vs Town undecided -> Geospatial Region); else bfo:entity (abstain).
4. The record's class is its first real sentence's -- the one that says
   what the subject is (averaging every sentence dilutes it: held-out full
   records 45.6% exact for the mean vs 72.8% for the first sentence, at the
   earlier threshold). Per-sentence classes and confidences go out as
   `sentence_ontologies` / `sentence_confidences`.

Without a parse the head abstains with `abstained: "no_parse"`. It refuses to
start without a codebook artifact that matches this build: feature spec,
parser fingerprint (sha256 of the cues extracted from the 300 fixed texts in
`artifacts/parser_probe.json` -- a parser refactor that keeps its output keeps
the fingerprint; one that changes what the head sees fails closed), TBox,
class list, shapes, IDF weights.

## How an entity gets its class (bundler)

From the ontology head only: the record's class, for every entity in the
record (Einstein's Nobel Prize address is Person). Only if the head abstained
on the record: the classes of the sentences containing the entity, voting with
the head's confidence; else bfo:entity. NER labels and the entity codebook do
not override it.

## Query

- The coordinator looks up each query entity's stored classes from the graph
  index (`KvInvertedIndex.entity_classes`, injected as `entity_classes_fn` by
  the query server); they are added to the bundle and lead the planner hints.
- The planner's tiers are BFO's top-level branches; every class the active head
  can emit (`emittable_classes`) and every hinted class joins its branch's
  tier, so its partitions are planned. Within a tier: hinted classes first,
  then classes related to a hint by subsumption.
- The head's classification of the query text is a soft preference only.

## Codebook training

- **Labels.** Each wiki record's subject: Wikidata "instance of" walked up
  "subclass of" to the nearest anchor in `training/cco_anchors.py` (anchors
  -> CCO classes, each row stating the Wikidata label it was checked against;
  disambiguation pages excluded). List articles, discographies and timelines
  are Descriptive Information Content Entity (`cco:ont00000853`): they
  describe a set. `scripts/ontology/fetch_wikidata_*.py`
  fetch the labels (resumable).
- **Examples.** Sentences about the subject (a list-style title fragment;
  the first real sentence; later ones whose subject is a pronoun or the title), from the text exactly as the DCP
  adapter publishes it, parsed by the production backend.
- **Classes.** A class needs `--min-support` training records (150); short
  classes roll up to their nearest supported ancestor, recorded in the artifact.
- **Centroids.** IDF weights from the training split; per-class spherical
  k-means; LVQ refinement (own-class centroid pulled in, nearest other-class
  centroid pushed out).
- **Calibration.** Temperature minimises validation NLL over all sentences;
  the acceptance threshold and an optional top/runner-up margin ratio are set
  on validation records' first sentences (what decides a record's class), as
  the lowest values at which accepted predictions reach the precision target
  (0.85). Test is reported only.

## Measured

Full corpus (120,000 records; 108,487 labelled, 330,379 subject sentences;
46 classes after roll-up), held-out test split, record level = the record's
first sentence with cues as the head ships it, same records and production
text for every head (runtime-verified offline 2026-10-04;
`artifacts/cco_codebook.json` `eval`, `training/cco_baseline.py`):

| held-out records | sketch head (retired) | CCO codebook |
|---|---|---|
| exact class | 22.1% | 77.5% |
| exact or correct-but-coarse | 22.1% | 82.4% |
| abstained | 39.5% | 0.3% |
| precision when it commits | 36.6% | 82.7% |

(10,810 records for the codebook; the sketch head was scored on the 10,581
of them labelled before list pages were.) List and index pages: 184 of 189
held-out list-titled records exact (97.4%); over the whole corpus 2,100 of
2,137 list-titled pages are typed Descriptive ICE, the rest mostly
"Index of ..." -> Document Content Entity. Descriptive ICE on held-out
records: precision 0.88, recall 0.83.

The sketch head typed 59% of records Person (Person is 30% of subjects) and
abstained on 39.5%. Acceptance threshold 0.20 (calibrated to 0.85 precision
on validation first sentences).

In-process pipeline on `wiki_100.jsonl` (heads -> bundler -> builder, the
NATS stage's per-sentence calls; offline 2026-10-04): 4,089 address keys, every
type segment a certified class, one class per bundle, Person 26.9% of addresses.

Weak spots: the trained `bfo:material entity` class (chemical kinds, minerals,
proteins, anatomy) attracts technical concept articles; defining nouns rare in
training ("philosophy") misfire (Anarchism -> Material Artifact).

Before the change, on Hetzner (100k corpus, runtime-verified 2026-10-03): 80%
of 2,042,071 addresses typed `person`; 45,457 of 766,358 entities (5.9%) stored
under more than one type.

## Limits

- Typing kinds that BFO does not model as particulars is a judgment call,
  stated in `cco_anchors.py`: taxa -> Organism, chemical kinds -> material
  entity, fictional characters / works / disciplines -> Information Content
  Entity.
- Moving to the CCO key format needs a flush and reload; the attribute,
  affordance and context stores need reseeding (their overrides are keyed by
  class).
- Downstream consumers re-keyed to classes (attribute/affordance relevance,
  exemptions, overrides; context DOMAIN_SEEDS) keep their old behaviour per
  class; their tuning against the new classes is open work.

## Second head: gaius (TBox verbalization + MaxSim)

`src/nam_heads/impls/ontology/gaius/` holds a second ontology head. It
fills the same slot (`head_type="ontology"`, contract `ontology-v1`) and is
fully independent of the codebook head. It runs only while the head-slot manifest selects
it.

It is inspired by github.com/zndx/gaius, a method chosen by NAM's maintainer. It does
not reproduce it (`docs/research/gaius-fidelity-audit.md`):
- gaius types against its SDG ontology (905 classes as its loader reads it), with raw text and the
  ColBERT-Zero weights;
- this head types against BFO/CCO, with a parsed noun phrase and
  ModernColBERT-embed-base weights.
The faithful reproduction is `impls/ontology/gaius_ref`.

How this head works:
- Each class is verbalized as "label. definition", from the pinned TBox.
- The verbalizations are embedded with ModernColBERT-embed-base (onnxruntime,
  fp32; the asset path keeps the name `colbert-zero-onnx`).
- A record's defining phrase from the rule parse ("a German-born
  theoretical physicist") is typed by MaxSim retrieval over 69 classes: the
  active set minus bfo:entity and the BFO top categories.
- Classification needs no training. The softmax temperature is fitted on
  validation records, and the acceptance threshold is 0, so the head
  commits to its top class.

Offline (2026-10-07), on the codebook's 10,810 held-out test records:

| | gaius | codebook |
|---|---|---|
| exact | 32.2% | 77.5% |
| exact or coarse | 34.3% | 82.4% |
| abstained | 0.0% | 0.3% |
| Person | 23.7% | 30.5% (gold 29.6%) |

The two heads agree on 32% of records. Gaius costs ~120-146 ms/record on
one thread (M3 Pro), against ~1-2 ms for the codebook, and its process
needs ~750 MB RSS.

The design, the measurements and how to run it are in that package's
README.md. The full report is in `artifacts/eval_test.json`.
